# Evaluation v5 pre-registration

[简体中文](zh/evaluation-v5-prereg.md)

Status: **frozen design and thresholds**, written before any v5 tuning. The only permitted later edits are the freeze metadata (commit, fixture hash, report hash) and an explicit changelog entry that forces a rerun. Changing a task, rubric, threshold, arm, schedule, or analysis after seeing a result is a failed run, not a new plan.

## Why v5 replaces v4

The Phase A1 audit ([evaluation-audit.md](evaluation-audit.md)) found that the v4 accuracy suite is a single-request exact-string pressure test, its synthetic fixed-line facts are overfittable, it has no held-out split or gold/degraded controls, and its region labels are rendering positions rather than semantic categories. v4 remains a historical regression instrument; it is not the v5 gate.

## Task set

**Corpus**: a generated, task-level engineering scenario for a fictional project. Each scenario contains a long working history (target 70,000–90,000 estimated source tokens) with user requests, assistant messages, tool calls, tool results, build/test logs, file listings, stack traces, and incident notes. Facts are embedded in the messages that a real session would contain, not in a uniform padding template.

**Turns**: 10 fixed turns. Each turn asks 4 questions in one user message and expects one JSON object. The persistent history appends the question, the assistant answer, and (for the offline recall reference only) tool traffic. The schedule is fixed and is not sampled per run.

**Questions**: 40 total, 4 per turn, in a fixed pre-registered order. The coverage is:

| Class                 | Count | What it tests                                                        |
| --------------------- | ----: | -------------------------------------------------------------------- |
| Exact command         |     4 | Shell command line, flags, and order                                 |
| Exact path            |     4 | Absolute or repository-relative path                                 |
| Exact checksum        |     4 | Digest with case and separators                                      |
| Exact identifier      |     4 | Env var, feature flag, lock name, version token                      |
| Numeric               |     3 | Port, timeout, retry count, version number                           |
| Cross-region semantic |     6 | Combine a head constraint with a tail decision, or two distant facts |
| Temporal / causal     |     6 | What happened after a failure; which action caused which state       |
| Negation / constraint |     5 | What must not be done, excluded, or used                             |
| CJK                   |     4 | Chinese incident note, identifier, or instruction                    |

Exact-string questions are 16/40 = 40%. They are not down-weighted. Every question has a deterministic rubric derived from the source text:

- `exact`: trim outer whitespace, strip one surrounding backtick/quote pair (Markdown presentation), and accept one terminal `.`/`。`; otherwise character-for-character, including case and internal separators.
- `all`: every required literal token is present and no forbidden decoy token is present. Required tokens come from the source sentence, not from a model.
- `any`: at least one accepted literal is present, and no forbidden token is present.

No model judges an answer. The rubric is generated by the same generator that writes the scenario and is stored next to the source snippet.

**Decoys**: at least 20 plausible false facts (wrong port, wrong path, stale checksum, deprecated flag) in the history. A decoy must not contain a correct answer's source text and must not be asked. The generator asserts this.

**Leakage**: the question prompt contains only the question text and the JSON key. It does not contain the answer, the rubric, the source line, or the region. The test fixture is generated into `.artifacts/bench-v5/test/` and is not committed. The repository contains only the generator, the seeds, and the hashes.

**Splits**:

| Split |     Seed | Committed?                                | Use                                                              |
| ----- | -------: | ----------------------------------------- | ---------------------------------------------------------------- |
| dev   | 20261112 | Seed and generator only                   | Iteration, renderer/serialization tuning, measurement validation |
| test  | 20261113 | Seed, generator, and fixture SHA-256 only | Final acceptance, once, after the freeze                         |

The test fixture is generated by the committed generator at the frozen commit. The generator prints only its SHA-256 and counts; its content is not inspected before the final run. The dev fixture may be regenerated at any time from its seed.

## Arms

| Arm               | Input                                                                                                                                         | Tools   | Purpose                                                                             |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------- | ----------------------------------------------------------------------------------- |
| `original`        | Full fixture history                                                                                                                          | None    | Control; no compaction                                                              |
| `native-text`     | Native summary generated once from the full history                                                                                           | None    | Host baseline                                                                       |
| `pure-visual`     | Production checkpoint: bounded exact head/tail + bitmap middle + a bounded, deterministic exact-token text index (no tools, no archive)       | None    | Target                                                                              |
| `gold-text`       | Same head/middle/tail selection and exact-token index as pure visual, middle as exact text, no frames                                         | None    | Comprehension ceiling                                                               |
| `degraded-visual` | Production checkpoint with each frame downscaled 50% and nearest-neighbor upscaled, every other frame kept, and the exact-token index omitted | None    | Renderer/checkpoint negative control                                                |
| `recall-ref`      | Production checkpoint + offline archive recall                                                                                                | Bounded | Non-inferiority reference only; never registered in production; deleted at Phase B4 |

The exact-token index is part of the checkpoint, not a recall tool: it is generated from the same serialized history as the frames, is capped at 80 labeled lines, and contains no question or answer generated by a model. It exists because 64-character digests are not reliably readable from pixels; the frames still carry the surrounding history. The report calls this arm `pure-visual` for continuity with v4, but the product description must disclose the index.

All arms use the same persistent 10-turn history and the same questions. Each turn has a 32,768-token output ceiling; hitting the ceiling fails that run instead of scoring a truncated answer. The four main arms have no tools. `recall-ref` may call the offline archive at most twice per turn and at most 20 calls total; a call over the cap is an error and the arm answers without tools. Its archive is created by the harness, not by a committed compaction.

## Route and decoding

The benchmark uses the configured route and model. Production, native and degraded arms set the provider-compatible `reasoning_effort: low` to bound hidden reasoning and keep the 10-turn schedule feasible; the gold-text ceiling arm uses the provider default so the ceiling is not limited by a decoding constraint. Every arm still receives the full checkpoint and the same questions. A provider that ignores the field uses its default. The route, model and per-arm reasoning setting are recorded in the run log. Changing this setting after the freeze requires a new freeze and a full rerun.

## Scoring and analysis

Per arm, per run:

- accepted score / 40; exact-string subset / 16; per-class and per-region tallies;
- per-question outcome with expected, given, rubric, and pass/fail;
- per-turn score, prompt tokens, peak single-request prompt, output tokens, cache read/write, weighted cost, model requests, recall calls/bytes, elapsed time;
- usage audit per request; any positive `unreportedPrompt` fails the run;
- character error rate for missed questions, split by expected character class (uppercase, lowercase, digit, punctuation, CJK, other);
- parse mode (raw JSON, extracted JSON, failed).

Cost:

```text
prompt    = input + cacheRead + cacheWrite
weighted  = input + 0.1·cacheRead + 1.25·cacheWrite + 4·output
```

Weighted cost is a relative unit, not a bill. Cost is reported per turn and per arm, plus peak single-request prompt and the ratio to `original`. The native summary generation is amortized into the native arm. Rendering time is excluded from model cost and reported separately.

Statistics:

- 3 runs per arm on dev and 3 on test. Report mean, min, max, and a 95% confidence interval using the t distribution with n−1 degrees of freedom (n=3, t=4.303). The interval is descriptive; the acceptance decision uses the mean.
- Report per-run and pooled per-question pass rates. A question that passes 2/3 runs is not silently counted as a pass; the mean is the score.
- If a run fails (provider error, usage audit, malformed response), report it as failed. Do not replace it with a synthetic rerun. A final test with fewer than 3 measured runs fails the measurement gate.

## Frozen thresholds

The primary gate is **pure visual on the test split**, mean of 3 measured runs:

| Gate                                             | Threshold                                                           |
| ------------------------------------------------ | ------------------------------------------------------------------- |
| Overall accepted                                 | **≥ 38/40 (95%)**                                                   |
| Exact-string subset                              | **≥ 15/16 (93.75%)**                                                |
| Cross-region semantic                            | **≥ 5/6**                                                           |
| Temporal / causal                                | **≥ 5/6**                                                           |
| Negation / constraint                            | **≥ 4/5**                                                           |
| CJK                                              | **≥ 3/4**                                                           |
| Numeric                                          | **≥ 2/3**                                                           |
| Head region (diagnostic)                         | **≥ 6/7**                                                           |
| Tail region (diagnostic)                         | **≥ 5/6**                                                           |
| Middle region (diagnostic)                       | **≥ 25/27**                                                         |
| Non-inferiority vs `recall-ref` on the same test | **pure visual ≥ recall-ref − 1 question** (≤ 2.5 percentage points) |

The non-inferiority gate is the binding one when recall scores 40/40: pure visual must score at least 39/40. The absolute gates are not relaxed to make that easier; both must hold.

Cost gates on the test split, pure visual vs original:

| Gate                              | Threshold            |
| --------------------------------- | -------------------- |
| Peak single-request prompt        | **≤ 0.40× original** |
| Total weighted cost over 10 turns | **≤ 0.78× original** |

## Measurement-instrument acceptance

Before the test is allowed to decide anything, the same test run must show:

1. **Ceiling (v5.1)**: `gold-text` mean ≥ 38/40 and ≥ pure visual − 1. Gold-text is the comprehension ceiling; a low gold score means the task or rubric is broken, not that the renderer is good. The one-question tolerance is the authorized v5.1 deviation described in the changelog; product gates are unchanged.
2. **Negative control**: `degraded-visual` mean ≤ 32/40 and at least 4 questions worse than pure visual in the paired run. The control removes the exact-token index and keeps every other frame in addition to the 50% downscale, so it tests the frame path rather than the text index. If degradation does not hurt, the task does not depend on the frames and the result is not evidence.
3. **Ordering**: gold-text ≥ pure visual ≥ degraded-visual. Equality is allowed only between gold and pure visual; pure visual must be strictly above degraded.
4. **No leakage**: the generator's assertions pass; no question prompt contains its answer or rubric; no decoy contains a correct source; the test fixture hash matches the frozen hash.
5. **Reproducibility**: regenerating a fixture from the same seed produces the same SHA-256; rerunning the analysis on the same JSON produces the same report hash.
6. **No test tuning**: the frozen commit and test hash predate the first test run. Any code change after the freeze is recorded and forces a new freeze, a new test generation, and a full rerun.

A failure of any instrument-acceptance item invalidates the test result even if the product gates pass. Report it; do not select the passing subset.

## Reporting

The v5 report must include:

- fixture id, seed, SHA-256, generator version, commit, and report hash;
- the fixed schedule and every question's class, region, rubric, expected answer, and given answer;
- per-arm, per-run, per-turn, per-class, per-region, and per-character-class results;
- means, min/max, and 95% intervals;
- usage audit and weighted cost, with the peak and total ratios;
- the instrument-acceptance table and the product-gate table, each with pass/fail;
- the v4 historical numbers in a separate table, clearly labelled as a different instrument;
- every retracted or retained v4 conclusion, with a reason;
- failed runs and any deviation from this plan, including the changelog entry that authorized it.

The test report is written under `.artifacts/bench-v5/test/` and is not committed. The committed summary contains only aggregate numbers, hashes, and the pre-registered analysis.
