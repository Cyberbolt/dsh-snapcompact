## 评测 v3

**2026-11-11** 用路由 `opencode-go/deepseek-v4.1-flash`、语料 `engineering-recall-v3` 执行的真实合成语料运行，三次运行。它使用生产渲染器、原生摘要引擎和 `evaluate()` 路径；没有读取或上传私密会话历史。

原生摘要用 21,434 生成 token（36.0s）。视觉 checkpoint 为 5 帧，估算 8,367 token，低于 8,426 token 的半源预算，准备耗时 0.9s。归档完整保留 40 条 source。recall 臂平均每次运行 2.0 次批量工具调用、2.3 个模型轮次，工具结果序列化后 20,366 字节。

### 这组数字说明什么

- **出厂配置与原始历史打平，同时保留精确回查，且比逐题回查便宜得多。** `snapcompact-recall`——会话真正收到的 checkpoint（帧 + `snapcompact_recall` 工具）——39.7/40，与原始历史同均值；三次运行里两次 40/40，唯一失分是 `t_next`，也正是对照臂唯一失分的那题。原生摘要 37.7/40，丢的是头段事实：中文约束被截断成前半句，一处否定句丢了原标点。只用帧的 `snapcompact` 是 33.0/40，说明归档在真正干活。
- **渲染器在结构化文本上准确，在随机串上不准确。** 四个臂的头段只要保持逐字都是 21/21；只用帧的臂保住 39/60 中段事实。它的每一处失分都是随机 token（审计 id、checksum、request id、回滚后缀），而且若干错误值（`AUDIT-9F3C-7B2`、`CRC32:9e2f31ac`）在语料里根本不存在。这是"自信地编一个像的值"，也是上游 omp 记录过的失败模式，不是排版缺陷。
- **recall 把漂移变成精确。** 每次调用最多批量 20 条字面量，中段仍是 60/60、尾段 38/39。检索打的是模型能读对的标签（`Observation 240:`），所以读错的值不会污染查找。
- **批量查询是 token 的主要杠杆。** checkpoint 是 6,813 token，承载 63,423 字符历史；每个工具轮都会重发它。两次批量调用、2.3 个轮次把每轮读取降到 18,341（逐题单独调用时是 30,841），3 轮投影降到 55,022（原 92,524）。一次 20 条批量约 14k 字符，仍比它省掉的 checkpoint 重发便宜得多。
- **严格匹配现在高于原生。** 37.3 vs 35.0：`X-Snap-Trace: 5b7e9c1d` 或 `PRIMARY-ONLY until further notice.` 这类带标签/整句的引用算接受匹配，但不是裸的规范串。接受匹配是主分，因为答案在事实上是对的。

单次运行可能让一两道题波动；以上数字合并了三次运行。需要范围时在自己的路由上跑 `/snapcompact benchmark 3`。
