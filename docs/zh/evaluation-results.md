## 评测 v3

**2026-11-11** 用路由 `opencode-go/deepseek-v4.1-flash`、语料 `engineering-recall-v3` 执行的真实合成语料运行，三次运行。它使用生产渲染器、原生摘要引擎和 `evaluate()` 路径；没有读取或上传私密会话历史。

### 这组数字说明什么

- **出厂配置已经打平并超过原生摘要。** `snapcompact-recall`——会话真正收到的 checkpoint（帧 + `snapcompact_recall` 工具）——三次运行全部 40/40。原生摘要 38.3/40，丢的是头段事实：中文约束被截断成前半句，一处否定句丢了原标点。只用帧的 `snapcompact` 是 34.0/40，说明归档在真正干活，不是装饰。
- **渲染器在结构化文本上准确，在随机串上不准确。** 四个臂的头段只要保持逐字都是 21/21；只用帧的臂保住 43/60 中段事实。它的每一处失分都是随机 token（审计 id、checksum、request id、回滚后缀），而且若干错误值（`AUDIT-9F3C-7B2`、`CRC32:9e2f31ac`）在语料里根本不存在。这是"自信地编一个像的值"，也是上游 omp 记录过的失败模式（它为 0/O 混淆发过修复），不是排版缺陷：头段满分，且每个 token 都在同一行内。
- **recall 把漂移变成精确。** 每个精确串题做一次 search，中段 60/60、尾段 39/39。检索打的是模型能读对的标签（`Observation 240:`），所以读错的值不会污染查找。
- **成本转移到了工具循环。** checkpoint 本身是 6,803 token，承载 63,423 字符历史；recall 臂 30,841 的每轮读取，是单回合回答 40 题时做 24 次校验调用带来的，不是稳态成本。一次 search 只返回几行，会话里问一个精确串就只付一次小查询。
- **严格匹配低于原生。** 36.7 vs 37.3：`X-Snap-Trace: 5b7e9c1d` 或 `PRIMARY-ONLY until further notice.` 这类带标签/整句的引用算接受匹配，但不是裸的规范串。接受匹配是主分，因为答案在事实上是对的。

单次运行可能让一两道题波动；以上数字合并了三次运行。需要范围时在自己的路由上跑 `/snapcompact benchmark 3`。
