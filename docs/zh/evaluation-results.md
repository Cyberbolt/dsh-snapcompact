# 评测结果

## 当前格式：本地渲染测量

以下数字来自当前的连续流排版和 1-bit PNG 编码器。它们是渲染测量，不是模型召回分数，也没有发起任何模型调用；fixture 那一行渲染的是触发预算裁剪前的完整位图中段。

| 语料 @ 1568×1568                                | 帧数 | 每帧内容字符 | PNG 总量 | 每帧 PNG |
| ----------------------------------------------- | ---: | -----------: | -------: | -------: |
| `engineering-recall-v2` 位图中段（67,888 字符） |    5 |       13,380 |  55.2 KB |  11.0 KB |
| 带缩进代码语料（28,729 字符、960 行）           |    3 |        9,257 |  35.5 KB |  11.8 KB |

旧的逐行排版对一份 7 万字符语料需要 14 帧，每帧约 5.0k 字符，PNG 总量 792 KB。同一渲染路径由 [`src/rendering/density.test.ts`](../src/rendering/density.test.ts) 做回归约束：在合成散文和代码语料上固定帧数、每帧字符数和 PNG 字节数；具体字节数会随 zlib 构建略有差异。

阅读图例是 checkpoint 的一部分：`¶` 标记一个源换行，连续 `¶` 表示空行，行首空格保留缩进，写满后在帧边缘折行。

## 最近一次真模型运行：fixture v2（40 题、10 个中段 probe）

这是 **2026-11-10** 用 DSH `0.2.2-rc.1`、路由 `opencode-go/deepseek-v4.1-flash` 执行的真实合成语料运行，使用随包的 `engineering-recall-v2` 语料；没有读取或上传私密会话历史。运行使用生产渲染器和 `evaluate()` 路径，通过同一路由完成四次辅助模型调用；它不是给 v1 表换标签。

| 方案        | 状态     | 精确匹配 | 帧数 |  时间 | 说明                                                                    |
| ----------- | -------- | -------- | ---: | ----: | ----------------------------------------------------------------------- |
| original    | measured | 38/40    |    — | 33.2s | 完整 fixture 文本；未命中 `next`、`cjk_note`                            |
| native-text | measured | 40/40    |    — | 50.9s | 原生摘要基线；生成成本 20,361 token                                     |
| snapcompact | measured | 36/40    |    5 | 56.9s | 1568×1560 帧，估算 checkpoint 7,607 token；计价来源 `deepseek-estimate` |

视觉组答对 10 个中段 probe 中的 8 个。未命中键为 `constraint`、`next`、`probe_340`、`probe_420`；两个 probe 未命中分别是中文回滚路径和审计 token，另外两个是精确头尾事实。因此这次运行不能证明有位图中段时头尾文本一定被还原。

五帧共 56,545 字节（55.2 KiB）PNG，准备耗时 0.9s。视觉 checkpoint 估算为 7,607 token；provider 对视觉答题调用报告 6,717 prompt token。原生摘要生成使用 14,814 input、5,547 output token（合计 20,361），耗时 49.4s，之后每轮读取 1,515 token。Provider 的 output 计数包含 reasoning token，所以摘要正文本身小于 5,547 token。

### Token 账（fixture v2）

| 方案        | 一次性生成 | 每轮读取 | 首次压缩 | 3 轮合计 |
| ----------- | ---------: | -------: | -------: | -------: |
| original    |          0 |   15,107 |   15,107 |   45,321 |
| native-text |     20,361 |    1,515 |   21,876 |   24,906 |
| snapcompact |          0 |    6,717 |    6,717 |   20,151 |

- 视觉 checkpoint 在首次压缩时比摘要便宜（6,717 vs 21,876），3 轮合计仍然更便宜（20,151 vs 24,906）。在这个 fixture 上，摘要大约从第 4 轮开始反超。
- 原生摘要 40/40，而原文 38/40。单次固定语料运行可以出现这种顺序反转；这不能证明摘要保留了更多信息，只能说明这个 fixture 的题目可以从该摘要回答。
- 40 题运行需要 32,768 token 的输出上限。旧的 8,192 上限会让原文组和视觉组在作答前触发 `max-tokens`，因而没有分数；这是评测工具的限制，不是召回结果。

## 上一次真模型运行：fixture v1（9 题）与旧渲染器

这一节是历史记录，测量于连续流排版和 fixture v2 之前。不要把下表当作当前格式的成绩。

这是 **2026-11-09** 用 DSH `0.2.2-rc.1`、路由 `opencode-go/deepseek-v4.1-flash` 执行 `/snapcompact benchmark` 的真实合成语料运行，使用随包的 `engineering-recall-v1` 语料；没有读取或上传私密会话历史。

| 方案        | 状态     | 精确匹配 | 帧数 |  时间 | 说明                                                                    |
| ----------- | -------- | -------- | ---: | ----: | ----------------------------------------------------------------------- |
| original    | measured | 8/9      |    — |  9.4s | 完整 fixture 文本                                                       |
| native-text | measured | 7/9      |    — | 12.5s | 原生摘要基线                                                            |
| snapcompact | measured | 8/9      |    6 | 16.3s | 2048×2040 帧，估算 checkpoint 8,786 token；计价来源 `deepseek-estimate` |

原生摘要使用 112 input、14,464 cache-read、1,476 output token（合计 16,052）。视觉组没有 handoff 调用；它渲染并读取位图帧。

benchmark 直接调用视觉方法，并套用引擎在没有实时触发阈值时使用的“源历史一半”上限。正常会话里 checkpoint 必须落进触发阈值推导出的预算（阈值以下剩余空间的一半，且不超过源历史的一半），所以短历史即使测量出的 checkpoint 更小，也可能回退文本。

### Token 账（fixture v1）

这些是 token 总量，不是账单金额。prompt 总量遵循 DSH 合同：input + cacheRead + cacheWrite。一次性生成是产出 checkpoint 的成本；每轮读取是之后携带的上下文。

| 方案        | 一次性生成 | 每轮读取 | 首次压缩 | 3 轮合计 |
| ----------- | ---------: | -------: | -------: | -------: |
| original    |          0 |   14,357 |   14,357 |   43,071 |
| native-text |     16,052 |      523 |   16,575 |   17,621 |
| snapcompact |          0 |    8,152 |    8,152 |   24,456 |

- 原生摘要在首轮之后每轮都更小，但生成它一次性要多花约 16k token。只比较它 523 token 的读取量和视觉 checkpoint 的 8,152 token，会漏掉这次生成调用。
- v1 视觉 checkpoint 在首次压缩时更便宜（8,152 vs 16,575）；在这个 fixture 上，摘要大约在第 2–3 轮之间反超。
- 缓存读取通常比fresh input 便宜，图片计价也因路由而异；这些总量不是账单。

## 解释

- **可读性：** v1 里视觉组和原文一样 8/9，但计分事实全部落在 2,000 字符的精确 tail 里，所以那个分数没有证明模型读了位图。v2 把 10 个 probe 放进位图中段，视觉组答对 8/10，包括带缩进的 Python helper；两个 probe 未命中是中文路径和审计 token。这是这里第一个真正依赖帧读取的分数。
- **Token 经济性：** 上表的 v1 数字是历史数据。当前排版在 1568 下每帧多装约 2.7 倍字符，PNG 帧更少也更小，因此旧的帧数和每轮总量不能外推为当前构建的预测。
- **什么时候适合视觉：** 长历史、图片 token 便宜的路由、不能接受有损摘要的保真任务，以及不想发起摘要调用的溢出恢复。
- **运行间波动：** 同一 v1 语料更早一次运行（07:46 UTC）测得 original 8/9、14,357 prompt token，native-text 8/9、639，snapcompact 8/9、8,149、6 帧。精确匹配结果会在一次运行间波动一题。
- **评测范围：** v2 是合成、固定、更大的语料（40 题、10 个中段 probe），但仍不代表所有语言、provider 或长期项目。
